# Design
Use extend_doctype_class for POS Invoice, with a mixin overriding only validate_pos_opening_entry. Resolve existing per-company settings using the authoritative invoice company/profile; require opt-in and primary profile equality. Query the same global open profile set as native validation; never filter away duplicates. Zero/multiple openings delegate to native super. A single opening must be submitted, company-consistent with invoice/profile, have a valid non-future start, and match any existing restaurant opening reference. Current-day openings delegate to native; only valid older openings bypass the same-day restriction.

Add Check allow_permanent_pos_opening default 0 to existing company settings; preserve permissions. Reload only that DocType (settings table adds one flag column); no financial table/data migration. Never run after_migrate/backfill. APIs/reports/fixtures/patches: no changes. Other native invoice validations and Sales Invoice stay unchanged. Scope targets v16, despite older v15 documentation.

Development unit tests use mocks and actual native validators with no invoice saves/submissions. Runtime tests in read-only transactions verify actual MRO/default-off and old valid opt-in behavior. Production activation only on the approved company's primary profile after tests; targeted web reload for the new Python hook. Compare opening snapshot and historical financial fingerprints around configuration changes, recognizing concurrent live transactions may occur.

Rollback: disable the flag using native settings save, clear relevant cache and reload web if reverting source. This restores native stale-opening rejection without closing or changing any opening/invoice. Revert the dedicated commit if needed; additive settings field can remain disabled. No external integration or tax payload changes.
